## 1. 项目概况与开发目标

| 项 | 内容 |
| --- | --- |
| 项目 | 小型智能仓储库位分配仿真系统（教学与辅助决策工具，非生产级 WMS） |
| 团队 | 3 人：a（数据底座 + RBAC）、b（推荐引擎 + 方案对比）、c（仿真引擎 + 可视化） |
| 技术栈 | Java 17 + Spring Boot 3.2.5 + MyBatis-Plus 3.5.5 + MySQL 8 + Flyway；Vue 3 + TypeScript + Vite + Element Plus + ECharts |
| 交付规模 | 12 张表、**63 个 REST 端点**（62 个契约接口 + 1 个健康自检）、8 个前端页面域、**176 个后端测试方法**、2 个一键验收脚本 |
| 关键路径 | 推荐评分模型（b）与仿真引擎（c）为核心算法；RBAC 以中间件横切（a） |

**开发目标**（对应《需求分析文档》第 11 节 8 条验收标准）：可建模、可推荐、可仿真、可对比、可导出、可鉴权、可复现、有文档。

## 2. 开发方法与协作约定

项目严格按《代码规范》与《任务分工文档》执行，以下约定在过程中确实起到了作用（也在第 6 节记录了它们失效的那一次）：

| 约定 | 落地方式 | 过程效果 |
| --- | --- | --- |
| 冻结契约优先 | 数据库 schema（Flyway V1~V3）、REST 接口清单（API-001~062）、鉴权中间件（`@PreAuthorize` + 权限码）、平面图组件 props（COM-5）、距离口径（COM-6）在第 1 周冻结 | 三人可并行；耦合点只有 5 处，且都用「数据结构」而非「函数调用」解耦 |
| 分支模型 | `main` ← `dev` ← `feature/a-*`、`feature/b-*`、`feature/c-*` | 分支隔离有效，但**合并环节出过一次严重事故**（见 P1） |
| 提交规范 | Conventional Commits + 任务编号（如 `feat(recommend): ...（B-B1/B-B3）`） | 提交信息可直接追溯到任务清单，便于验收比对 |
| 分层与目录 | 每模块 Controller → Service → Mapper；算法为无状态 Service（NFR-4） | 算法可纯 JUnit 测试，无需启 Spring 上下文 |
| 插件式扩展 | `InboundStrategy` 接口 + `StrategyRegistry` | 新增第 7 种入库策略只需加一个 `@Component`，引擎与前端零改动（已在验收中确认） |
| 跨模块只走公开 Service | c 的 `smart` 策略调用 b 的 `ScoringEngine`；c 取订单调用 a 的 `OrderService` | 未出现跨模块直连 Mapper 的情况 |
| 阶段确认制 | 每完成一个阶段向项目负责人汇报（改了什么、怎么验证的、还剩什么），确认后再进入下一阶段 | 8 个阶段均有明确的「完成—汇报—确认」节点，避免返工扩大 |

**工具链实测版本**：JDK 17.0.18（Microsoft Build）、Maven 3.8.2、Node v24.15.0、MySQL 8.0.32。
工程级 `backend/maven-settings.xml` 把本地仓库固定在 `backend/.mvn-repo`（本机全局 Maven 配置的仓库路径不存在且镜像不可达，不加 `-s` 会直接失败）。

> 说明：本项目的补齐与整合阶段（第 5 节阶段四~八）在开发过程中使用了 AI 编程助手辅助生成与核查；
> 每一处改动都经过「编译 → 单元/集成测试 → 真实数据库接口验证 → 前端构建与联调断言」四道验证，
> 验证命令与结果见第 7 节，可原样复跑。

### 3.2 阶段一、二：契约冻结与并行开发

- 阶段一产出 4 份契约文档（需求/分工/接口/代码规范），并额外冻结两份补充说明：
  《数据库设计说明书》（12 张表数据字典）与《鉴权中间件规范》（`requirePermission()` 用法与 401/403 返回格式）。
- 阶段二由 b 先行开工：推荐引擎（评分四分量 + 权重配置 + 归一化）、方案对比、报告导出，
  以及前端三页。此时后端以 `InMemoryWarehouseDataRepository` 提供数据，**刻意不依赖数据库**，
  以便算法先行开发与单测——这个决定让 b 的算法在阶段二就完成了 T-1 单元测试。
- 阶段三由 a 落地数据底座：12 张表的 Flyway 脚本、MyBatis-Plus 实体与 Mapper、
  基础数据 CRUD、批量导入导出、JWT + Spring Security 鉴权中间件、用户/角色/权限管理。

### 3.3 阶段三：合并——一次被记录下来的事故（P1）

`dev` 依次合并 `feature_a`（PR #1）与 `feature_b`（PR #2）。合并**没有产生冲突标记**，
但结果是把两边的同名文件按「a 的内容 + b 的内容」**首尾拼接**在一起，共 **20 个文件**：

| 类型 | 文件 | 症状 |
| --- | --- | --- |
| 构建配置 | `backend/pom.xml`、`frontend/package.json`、`frontend/package-lock.json`、`frontend/tsconfig.json` | 出现两份 `<dependencies>` / 重复 JSON 键，Maven 与 npm 均无法解析 |
| 公共类 | `WmsApplication`、`ApiResponse`、`BizException`、`ErrorCode`、`GlobalExceptionHandler`、`application.yml` | 同一文件里两个 `public class` / 两份 `server:` 根键 |
| 领域实体 | `Location`、`Sku`、`Warehouse` | b 的内存模型与 a 的 MyBatis 实体被拼在一起，字段与 getter 各两套 |
| 前端骨架 | `index.html`、`App.vue`、`main.ts`、`router/index.ts`、`styles/main.css`、`api/http.ts`、`vite.config.ts` | 两份路由/两份 axios 封装/两份样式；**b 的三个页面在生效路由里根本不存在** |

**后果**：后端编译不通过、前端无法构建，`dev` 处于不可运行状态。

**为什么没有被立刻发现**：`npm run type-check` 原本是 `vue-tsc --noEmit`，而 `tsconfig.json` 是
「solution 式」配置（`files: []` + `references`），**这种情况下一个文件都不会检查**——
脚本每次都「通过」，制造了虚假的安全感（这一问题被记为 P9，已修复为 `vue-tsc --build`）。

### 3.4 阶段四：修复合并损坏

处理原则：**a 的脚手架与公共基础设施是超集，作为权威版本；b 的算法代码保留意图，只按 a 的实体与 http 封装做适配**。

| 处理方式 | 文件 |
| --- | --- |
| 恢复 a 的完整版本 | `pom.xml`、`application.yml`、`WmsApplication`、`ApiResponse`、`BizException`、`GlobalExceptionHandler`、`ErrorCode`（另追加 b/c 需要的 42217~42222 六个业务码）、`index.html`、`package.json(-lock)`、`tsconfig.json`、`vite.config.ts`、`main.ts`、`App.vue`、`router/index.ts`、`main.css`、`api/http.ts` |
| 以 a 的 MyBatis 实体为权威、补回 b 依赖的 API | `Location`（补便捷构造、`isFree()`、非表字段 `category`）、`Sku`（补 `skuCode` 别名与 `weightValue()/turnoverRateValue()/priorityValue()` double 视图）、`Warehouse`（补便捷构造） |
| 适配 | b 的评分引擎改用 `weightValue()` 等访问器（保持「BigDecimal 存取」契约不变）；b 的 `api/*.ts` 改走 a 的 `get/post/put/download`；报告导出由 `<a href>` 改为带鉴权头的 `download()` |

验证：`mvn -o test` → 80 项通过；`npm run lint / type-check / build` 全部通过。

### 3.5 阶段五：数据库一致性核对与代码侧对齐

**核对方法（可复现）**：把 `db/migration/V1~V3` 拼接后在旁路库 `wms_sim_check` 重建一遍，
再用 `SHOW CREATE TABLE` 与在用库 `wms_sim` **逐表比对**，并比对 5 张 RBAC 表的种子行数与密码哈希。

**核对结论**：**数据库侧没有任何偏差**——12 张表完全一致、种子数据完全一致、4 个账号的 BCrypt 哈希逐字节一致。
`backend/sql/schema.sql` 确实是 V1+V2+V3 的忠实拼接。**问题全部在代码侧**，逐项对齐见下表（详见《数据库设计说明书》6.2）：

| # | 代码侧问题 | 对齐处理 |
| :-: | --- | --- |
| 1 | `Plan` 是 7 字段裸 POJO，与 `plans` 的 14 列完全不对应，三个 JSON 列未映射（c 写不进、b 读不出） | 改造为真实体 + 三个**保留泛型**的自定义 TypeHandler；对外字段名由访问器从 `result` 透出，API 契约不变 |
| 2 | b 模块数据来自硬编码内存仓储，完全没连 MySQL | 新增 `MybatisWarehouseDataRepository` 作为默认实现；内存实现降级为 `wms.repository=memory` 时的离线演示实现 |
| 3 | 采用推荐只改 `status`、不写 `occupied_sku_id` | 新增 `occupyLocation(id, skuId)` / `releaseLocation(id)`，占用走条件更新 `WHERE status='free'` |
| 4 | `S_other` 品类匹配与「分区存储」都需要「库位分区」，但表里没有该列 | 不改表结构：分区由 `racks.aisle` 经 `wms.zone.aisle-category` 派生 |
| 5 | b 的三个 Controller 缺权限注解 | 按《接口文档》权限列逐个补 `@PreAuthorize` |
| 6 | 手工按 `schema.sql` 建库的环境启动失败 | `baseline-version` 默认 3，Flyway 认领既有结构（见 P6） |

### 3.6 阶段六：成员 c 后端（API-054~062）

按《任务分工文档》4.3 与《接口文档》第 12~14 节实现 C-B1~C-B8：

- **策略框架**：`InboundStrategy` 接口 + `StrategyRegistry`（Spring 注入全部实现建索引），
  六种策略：`random`（种子固定可复现）/ `nearest` / `zoning`（分区命中后区内就近，未命中显式说明并退化）/
  `grading`（weightNorm×layerScore + turnoverNorm×proxScore）/ `smart`（复用 b 的 `ScoringEngine`）/ `fifo`。
- **仿真引擎**：逐项选位、每次选位立即在上下文中标记占用、记录 `{库位, 理由, 适配分, 告警}`；
  **全程不写 `locations` 表**（《数据库设计说明书》5.2「仿真需在不改库的前提下试算」）；
  「清空重置」= 丢弃内存记录 + 删除该次仿真产出的方案。
- **出库仿真**：订单按 `priority DESC, placed_at ASC` 排序；两种库存来源（方案 `location_map` / 真实占用）；
  逐单按「距出库口由近及远」跨库位取货凑数；统计总/平均/高频货平均路程与耗时估算。
- **距离口径（COM-6）**：`DistanceUtil` 统一三种口径，b 的 `ScoringContext` 也改为调用它，避免两套实现。

阶段产出 32 个新测试（距离 7 / 约束 7 / 策略 9 / 入库 6 / 出库 6），后端测试总数 80 → **115**。

## 5. 过程中发现并解决的问题

共记录 11 个问题，按「影响面」排序。每条都给出**现象 → 定位方法 → 根因 → 处理 → 验证**，便于复现与评审。

### P1 合并把 a、b 的同名文件首尾拼接（致命）

- **现象**：`dev` 上后端编译不通过、前端构建失败；同一文件出现两个 `public class`、两份路由。
- **定位**：对每个文件与 `feature_a`/`feature_b` 的内容做**逐文件比对**，筛出「与两边都不相同」的文件，恰好 20 个；
  再逐个人工确认是否为「两边内容拼接」。
- **根因**：合并工具/操作把同名文件按文本首尾拼接处理，且未留下冲突标记，因此 `git status` 看起来是干净的。
- **处理**：以 a 的脚手架为权威版本重建 20 个文件，b 的算法代码按 a 的实体/封装适配（详见 3.4）。
- **验证**：`mvn -o test` 80 项通过；前端 lint / type-check / build 通过。
- **教训**：合并后必须**跑一次完整构建**；「没有冲突标记」不等于「合并没有问题」；
  类型检查脚本若配置错误（P9），会给出虚假的安全感。

### P2 `Plan` 实体与 `plans` 表完全不对应

- **现象**：c 无法把方案写进库、b 无法从库读方案；方案对比只能吃内存里硬编码的 3 条数据。
- **根因**：`plans` 表有 14 列（含 `params`/`location_map`/`result` 三个 JSON 列），
  而 `Plan` 只是 7 字段裸 POJO——两者从未对齐过。
- **处理**：改造为 `@TableName("plans")` 实体；**不用** MyBatis-Plus 自带的 `JacksonTypeHandler`
  （3.5.5 只接收 `Class`，泛型在运行时丢失，`Map<String, LocationOccupancy>` 会退化成 `LinkedHashMap`
  并在取值时 `ClassCastException`），改为自建保留 `TypeReference` 的处理器基类；
  对外字段名由 `getTotalDistance()` 等访问器从 `result` 透出，**API-049/051 契约不变**。
- **验证**：API-049 正确读出 `locationMap={"1001":{"skuId":3,"quantity":20}}` 与 6 项统计。

### P3 b 模块完全没连数据库

- **现象**：规格要求「MySQL 存储」，但推荐/对比的数据来自代码里硬编码的 1 仓库/36 库位/5 SKU/3 方案。
- **处理**：新增 `MybatisWarehouseDataRepository`（库位一次查全、货架批量取回派生分区，无 N+1）；
  内存实现降级为 `@ConditionalOnProperty(havingValue="memory")` 的离线演示实现，二者互斥。
- **验证**：MySQL 模式与 memory 模式分别实测（后者无库可跑，保留 README 承诺的「可独立运行」）。

### P4 容量约束三方不一致（由端到端验收暴露）

- **现象**：六种入库策略**全部**报 `42220 已无可用库位`，而仓库里明明有空位。
- **定位**：把 `locations.capacity` 与 `skus.size.volume` 打印出来对比：
  库位容量默认 `100`，而接口文档示例的货物尺寸是 `30×20×10 = 6000`——**每个 SKU 都放不进每个库位**。
- **根因**：三处口径不统一：① DDL 默认容量 100；② 接口文档示例尺寸 6000；③ 只有 c 校验容量、
  b 的推荐引擎不校验——即「推荐得出来、仿真判为不可用」。
- **处理**：`SkuSize.fitsWithin(capacity)` 作为**唯一**判定，b 的 `ScoringEngine` 与 c 的 `ConstraintChecker` 共用；
  `CreateRackRequest` 增加可选 `capacity`（批量生成库位不再写死默认值）；货架表单与接口文档写明
  「容量与尺寸必须同单位」；演示数据统一取 100000。
- **验证**：六种策略各产出方案（总路程 23/23/26/26/60/90，符合「随机最差、就近最优」的预期）。

### P5 `plans.plan_no` 唯一键 vs 进程内自增计数器

- **现象**：应用重启后，第一次入库仿真报 `50001 数据库操作异常`。
- **定位**：看后端异常栈 → `Duplicate entry 'PLAN-20260927-001' for key 'uk_plans_plan_no'`。
- **根因**：方案编号只靠 `AtomicLong` 在进程内自增，重启后从 1 重来，而库里已有当天编号。
- **处理**：改为「查库取当前前缀最大编号 + 1」（`WarehouseDataRepository.findMaxPlanNo`），不再依赖进程内状态。
- **验证**：连续多次仿真编号递增不冲突（PLAN-20260927-004 … -010）。

### P6 手工建库的环境启动即失败

- **现象**：按 `schema.sql` 手工建过库的机器，应用启动报 `Table 'warehouses' already exists`。
- **根因**：手工建库不会产生 `flyway_schema_history`，Flyway 认为 V1~V3 待执行。
- **处理**：`baseline-version` 默认 3——库非空且无历史表时以版本 3 **认领**既有结构并跳过 V1~V3，
  空库首次启动行为不变；可用 `WMS_FLYWAY_BASELINE_VERSION` 覆盖。
- **验证**：启动日志 `Successfully baselined schema with version: 3`，且未改动任何数据（核对演示数据行数不变）。

### P7 Mockito 在受限环境不可用

- **现象**：带 Mock 的测试启动即报 `Could not self-attach to current VM using external process`。
- **定位**：异常链指向 ByteBuddy 的**外部进程自附加**机制被环境禁止；
  且 a 当年的注释也记录了这个现象，因此他用「不用 `@SpringBootTest` + 不用 Mock」绕开。
- **处理**：surefire `argLine` 增加 `-Djdk.attach.allowAttachSelf=true`，让 ByteBuddy 改为进程内自附加。
  **必须作为启动参数传入**：先试过 `systemPropertyVariables`，无效（JDK 在 `sun.tools.attach` 初始化时读取并缓存）。
- **验证**：新增的入库/出库服务测试（12 项，使用 Mockito）全部通过，总数 115。

### P8 端到端用例实际读写的是开发用真实库

- **现象**：跑 `-Pe2e` 时整批用例启动失败（`Port 8080 is already in use`），
  而用例本来用的是随机端口；日志里还出现 `Database: jdbc:mysql://.../wms_sim`。
- **根因**：6 个 e2e 用例都用 `SpringApplicationBuilder.properties(...)` 指定独立库
  （`wms_sim_e2e*`，其中一个本意是 H2 内存库），但 `properties()` 设置的是**默认属性、优先级最低**，
  会被 `application.yml` 的 `spring.datasource.url` 覆盖——即这些用例一直在读写开发真实库。
- **处理**：改为 `run("--key=value")` 命令行参数（优先级最高），独立库真正生效。
- **验证**：61/61 通过；5 个 e2e 库各自 13 张表，`wms_sim` 的演示数据未被触碰。

### P9 前端类型检查脚本长期空转

- **现象**：修复合并损坏前，`npm run type-check` 一直「通过」，但代码明显编译不过。
- **根因**：`tsconfig.json` 是 solution 式配置（`files: []` + `references`），
  `vue-tsc --noEmit` 在这种配置下**不检查任何文件**。
- **处理**：脚本改为 `vue-tsc --build --force tsconfig.app.json tsconfig.node.json`。
- **验证**：改完后立刻暴露出 5 处真实类型错误（b 的 api 模块引用了不存在的 `request` 导出等），逐一修复。

### P10 模板内联 TS 类型标注导致模板编译失败

- **现象**：`vue-tsc` 在模板表达式上报 `TS1005 ',' expected`（生产构建却正常，因为 Vite 的模板编译器容忍）。
- **根因**：Vue 模板表达式由模板编译器按 JS 解析，`(l: { status: string }) => ...` 这类标注不被接受。
- **处理**：把带类型标注的逻辑移到 `<script setup>`（如 `countByStatus`、`onLocationClick`、`onTogglePlan`），
  模板内只留函数调用。
- **验证**：type-check 全绿；该现象后来在验收阶段又被复现两次（写新页面时），已按同一方式修复。

### P11 端口改动只改了一半（交付后修正）

- **现象**：项目负责人把后端默认端口由 8080 改为 8081 后，前端「点击没反应」。
- **定位**：确认 8081 上有后端在跑、`/api/v1/health` 返回 401；但 `frontend/vite.config.ts` 的代理仍指向 8080。
- **根因**：端口在两处定义（后端 `server.port` 与前端代理目标），只改了一处；
  而当时 8080 上恰好还跑着另一个实例，掩盖了问题——排查时容易误判成「功能没实现」。
- **处理**：`vite.config.ts`、`preview-server.mjs`、`.env.example`、`env.d.ts`、`frontend/README.md`
  与三份文档统一到 8081，并在配置注释里写明「两处必须同步修改」。
- **验证**：停掉 8080 实例后，`npm run preview` + `verify:integration` 27/27、
  `acceptance.ps1` 47/47 全部通过（后端为 8081 上的实例）。

## 6. 关键设计决策与理由

| 决策 | 备选方案 | 最终选择与理由 |
| --- | --- | --- |
| 库位分区的存放方式 | ① 新增 Flyway V4 给 `locations` 加 `zone` 列；② 由 `racks.aisle` 派生 | 选 ②：不动已冻结的表结构，且「品类↔巷道」映射写在 `application.yml`，正好呼应 FR-2.3「权重与规则可配置」；未配置映射时按无分区约束处理，不影响可用性 |
| 仿真明细的持久化 | ① 内存保存、方案落库；② 新增仿真记录表 | 选 ①（按《数据库设计说明书》2.6 的约定）：仿真明细属过程数据，避免为它引入新表；代价是重启后明细失效，已在文档中写明 |
| 内存仓储的去留 | ① 直接删除；② 降级为可开关的演示实现 | 选 ②：保留 README 承诺的「无数据库可独立运行」，同时默认走 MySQL，两者由 `@ConditionalOnProperty` 互斥 |
| 重货层高约束的性质 | ① 硬约束（所有策略强制过滤）；② 软约束（判定 + 计数） | 选 ②：若所有策略都过滤，「重货层位违规数」这一对比指标恒为 0，FR-5.1 失去意义；与《接口文档》API-051 示例（随机违规 5、就近/智能为 0）的语义一致 |
| 搬运路程口径 | ① 往返双程；② 单程 | 选 ②：按《需求分析文档》1.4 术语表「从库位到出库口的移动距离」，每访问一个库位计一次单程，不按件数重复计；与 API-058 示例的数量级一致 |
| `plans.result` 的写入口径 | ① 只由出库仿真写；② 两段写入 | 选 ②：入库仿真先写「布局口径」（方案一产出就有可对比指标），出库仿真再用「订单口径」覆盖并补 `orderCount`/`estimatedTime`；两种口径都明确写在算法说明里 |
| c 的 `smart` 策略实现 | ① 复制评分逻辑；② 调用 b 的 `ScoringEngine` | 选 ②（《代码规范》4.5 明确要求）：避免两套评分模型漂移；代价是模块间耦合，用冻结的入参出参隔离 |
| 平面图渲染方式 | ① DOM 节点；② Canvas | 选 ②：万级库位下 DOM 方案会直接卡死（NFR-1 / 《代码规范》5.6 的建议） |
| JSON 列的类型处理 | ① MyBatis-Plus 自带 `JacksonTypeHandler`；② 自建保留泛型的处理器 | 选 ②：自带实现只接收 `Class`，泛型运行期丢失（详见 P2） |

## 8. 复盘：哪些做法有效、哪些需要改进

### 8.1 有效的做法（建议保留）

1. **冻结契约先行**：三人并行期间没有出现接口对不上的返工，耦合点只有 5 处且都用数据结构解耦。
2. **算法与框架解耦**：算法是无状态 Service，能纯 JUnit 测试；b 的算法在阶段二（还没有数据库时）就完成了单测。
3. **仿真不改库**：试算与真实占用分离，使「清空重置」「多策略对比」都变得简单且安全。
4. **插件式策略**：新增策略零改动扩展，验收时可以逐策略跑同一批入库明细做对比。
5. **脚本化验收**：`acceptance.ps1` 把 8 条验收标准固化成 47 条断言，任何人任何时间都能复跑。
6. **阶段确认制**：每个阶段结束先汇报与确认再继续，避免了「方向错了却做了很多」的浪费。

### 8.2 需要改进的做法

| 问题 | 改进措施 |
| --- | --- |
| 合并后未立即构建验证，导致损坏被带入 `dev` | 合并后必须跑「后端编译 + 前端构建 + 全量测试」；CI 上加一条合并流水线 |
| 类型检查/质量脚本长期空转，制造虚假安全感 | 质量脚本要么被 CI 强制执行，要么就别设；本次已把 `type-check` 修正为真正检查 |
| 关键约束（容量/尺寸）的口径没有单一实现 | 硬约束落到一处共享实现并配单元测试；跨模块复用的规则不各自实现 |
| 同一配置在两处定义（后端端口 / 前端代理） | 配置只留一处真源，另一处由它推导或环境变量注入；改配置时同步检查依赖方 |
| 过程数据（仿真明细）与结果数据混在一处讨论 | 明确「结果落库、过程内存」并写进设计文档（已在《数据库设计说明书》2.6 明确） |
| 页面反馈不足：结果在首屏之外、控制台无日志 | 长表单页操作后应自动滚动到结果区；关键操作至少留一条可观测痕迹（Network 或后端日志） |

### 8.3 如果重来一次

1. **第 1 周就把 5 处耦合点的数据结构写成代码骨架**（接口 + 空实现），而不是只写文档——本次 `Plan` 与 `plans` 的错位就源于「文档写了、代码没建骨架」。
2. **合并即构建**：把「编译 + 构建 + 全量测试」做成合并的前提条件，而不是事后补救。
3. **每个硬约束只实现一次**：容量、层高、一库位一货物这三条约束，从第一天起就放在共享位置并被推荐与仿真同时引用。
4. **验收脚本先写**：把 8 条验收标准在阶段二就翻译成可执行的断言，开发过程中随时知道「离验收还差什么」。
