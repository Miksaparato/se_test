## 2. P1：本轮迭代内应解决

### ISSUE-01 memory 模式实际仍依赖 MySQL（文档承诺不成立）

**现象与证据**

`README.md` 与《使用说明文档》都写着「**无 MySQL 也能跑**：加 `--wms.repository=memory` 可离线启动」。
实测把数据库地址指向一个不存在的端口后，应用**直接启动失败**：

```
ERROR com.zaxxer.hikari.pool.HikariPool : wms-hikari - Exception during pool initialization.
com.mysql.cj.jdbc.exceptions.CommunicationsException: Communications link failure
  ... at org.flywaydb.core.api.configuration.ClassicConfiguration.setDataSource(...)
Caused by: java.net.ConnectException: Connection refused: getsockopt
```

**根因**

`wms.repository=memory` 只替换了**业务数据访问实现**（`WarehouseDataRepository`），
但数据源、Flyway、MyBatis-Plus 仍按默认配置启动：

- HikariCP 在启动时 `checkFailFast` 建连，失败即抛异常；
- Flyway 初始化数据源时再次失败，上下文刷新中止。

而且这个模式**无法只靠关掉数据源解决**：`OrderService`（a 的模块）依赖 `OrderMapper`，
c 的出库仿真又依赖 `OrderService`，关掉 MyBatis 会导致这些 Bean 无法创建。

**影响**

- 与已交付文档的承诺不一致，评审按文档操作会失败；
- 「无数据库快速体验」这一卖点实际不可用。

**建议方案**（二选一，推荐 A）

- **A（推荐，约 0.5d）**：给 `memory` 增加一个 Spring profile，在这个 profile 下把数据源换成
  **H2 内存库**并关闭 Flyway（h2 已在测试依赖里，提为可选运行依赖即可）。
  这样 MyBatis 层照常工作、业务数据走内存仓储，真正做到「零外部依赖启动」。
- **B（约 0.2d）**：修正文档措辞为「memory 模式替换业务数据来源，但仍需要一个可连接的数据库
  （数据源与 Flyway 仍需初始化）」，并把该限制写进 README 与使用说明。

**验收标准**：在没有任何 MySQL 的机器上执行
`java -jar wms-sim-backend.jar --spring.profiles.active=memory`，能打印 `Started WmsApplication`，
且登录 → 推荐 → 入库仿真可跑通（或：文档已明确修正且不再宣称「无 MySQL 也能跑」）。

### ISSUE-02 库位容量默认值与接口文档示例尺寸冲突

**现象与证据**

- `locations.capacity` 的 DDL 默认值是 `100.000`；
- 《接口文档》API-030 的货物尺寸示例是 `30 × 20 × 10 = 6000`；
- 容量约束（《需求分析文档》4.4 约束三）会因此把**所有**库位判为「放不下」。

这个问题在本轮验收中真实发生过：六种入库策略**全部**报 `42220 已无可用库位`，逐项打印后才发现是单位口径问题。
当前的缓解手段是「文档提醒 + 货架创建时可指定 `capacity`」，属于**约定层面**，没有代码兜底。

**影响**

按接口文档示例录入数据的使用者，会在推荐与仿真环节直接踩坑，且错误信息（「无可用库位」）
指向的是症状而不是原因，排查成本高。

**建议方案**（建议同时做）

1. **数据层**：新增 Flyway `V4` 迁移，把 `locations.capacity` 的默认值调整为与文档示例同量级
   （如 `100000.000`），并同步更新数据库设计说明书与 `schema.sql`（属表结构变更，需三方评审）；
2. **应用层**：创建 SKU 时，若库位容量与该货物体积普遍不匹配，返回明确提示
   （例如「当前仓库库位容量为 100，而本货物体积为 6000，请先调整库位容量」），而不是等到推荐阶段报「无可用库位」；
3. **提示层**：导入 SKU 的模板里带一行说明，或在校验失败时把「容量 vs 体积」的具体数值写进错误信息
   （`ConstraintChecker` 已有数据，只需把提示补全）。

**验收标准**：按《接口文档》原文示例（容量默认、尺寸 30×20×10）建库建货物后，
推荐能正常给出候选库位；或在用户未调整容量时，第一个报错就明确指出是容量口径问题。

### ISSUE-03 审计日志覆盖不全，`plans.created_by` 从不写入

**现象与证据**

- `audit_logs` 表已建（V2），`AuditLogService` 也提供了通用 `record(...)` 方法，
  但**只有登录/登出在调用它**（`AuthService` line 86 / 102）；越权拦截
  （`RestAccessDeniedHandler`）只写了应用日志 `log.warn(...)`，未落库；
  入库、出库、采用推荐等关键路径均无审计记录。
- `plans.created_by` 列存在、实体也有 `setCreatedBy`，但**全项目没有任何一处调用**（已全仓检索确认），
  所以方案创建人恒为 `null`。

**影响**

《代码规范》4.6 要求关键路径（登录/入库/出库/推荐/越权）记录操作人、资源与结果；
当前无法回答「是谁跑的这个方案」「是谁触发了这次越权」。这属于**验收项之外但有明确规范依据**的缺口。

**建议方案**

1. 在 c 的入库/出库仿真、b 的采用推荐、a 的越权处理器中调用 `AuditLogService.record(...)`，
   记录 `action`（`simulate_inbound` / `simulate_outbound` / `adopt` / `denied`）、`resource`、`resourceId`；
2. 仿真保存方案时从 `SecurityContext` 取当前登录用户 id 写入 `plans.created_by`；
3. 注意脱敏：不记录密码、Token（规范已有明确要求）。

**验收标准**：跑一次入库仿真与一次越权访问后，`audit_logs` 中能查到对应记录且含操作人；
新建方案的 `created_by` 等于当前登录用户 id。

### ISSUE-04 验收/演示数据无法通过 API 清理

**现象与证据**

- 接口清单里**没有删除分配方案的端点**（API-049~053 只有列表/详情/对比/建议/导出）；
- 方案唯一能消失的方式是 API-057「清空重置」，而它要求提供 `simulationId`，
  且该记录保存在**进程内**——应用一重启就再也没有入口删除历史方案；
- `plans.warehouse_id` 的外键是 `ON DELETE RESTRICT`，因此只要该仓库下还有方案，
  仓库、以及它的货架与库位都无法删除。

实测后果：`acceptance.ps1` 每次运行都会新建一个验收仓库（`ACC-<时间戳>`）与 6 个方案，
跑几次之后演示数据里就会堆着若干删不掉的「僵尸仓库」，只能手工连数据库清理。

**影响**

演示环境越跑越乱；评审者按脚本自检后无法自行恢复干净状态。

**建议方案**（属契约变更，需按《代码规范》6 节先改《接口文档》再实现）

1. 新增 `DELETE /api/v1/plans/{id}`（权限 `sim:run` 或 `config:manage`），
   删除方案前校验是否为当前正在使用的方案；
2. 给 `acceptance.ps1` 增加 `-Cleanup` 开关：脚本结束时按记录的 id 依次
   删方案 → 删库位 → 删货架 → 删仓库 → 删验收货物（当前脚本已在末尾打印全部资源 id，改造成本很低）。

**验收标准**：执行 `acceptance.ps1 -Cleanup` 后，仓库数、库位数与方案数回到运行前的值。

## 3. P2：排入计划解决

### ISSUE-05 评分权重与分层规则配置存内存

- **现状**：`ConfigService` 的 `weights` / `rules` 是单例内的字段，重启即回默认值（0.30/0.40/0.20/0.10）。
- **影响**：FR-2.3 要求「权重与分层规则允许管理员调整」，管理员调完参数、应用一重启就白调了；
  且「智能推荐」策略与推荐引擎**同时**读这份配置，重启会造成历史方案与新推荐的评分口径不一致。
- **建议**：新增配置表（或复用现有的键值存储），把权重与规则持久化；接口行为不变。
  属于表结构新增，需 Flyway `V4/V5` 迁移与三方评审。
- **验收标准**：修改权重 → 重启应用 → `GET /config/weights` 返回修改后的值。

### ISSUE-06 推荐结果存内存

- **现状**：`RecommendationService` 用 `ConcurrentHashMap` 保存推荐结果（编号 `REC-<日期>-<序号>`）。
- **影响**：重启后 `GET /recommendations/{id}` 与 `POST /recommendations/{id}/adopt` 均返回 40409，
  前端「生成推荐 → 一键采用」的中间状态会断掉。
- **建议**：推荐结果落库（或放宽为「重启后需重新生成」并给出明确提示与前端引导）。
- **验收标准**：生成推荐 → 重启 → 查询该推荐仍能返回候选列表。

### ISSUE-07 仿真明细存内存

- **现状**：入库选位明细与出库拣选明细保存在 `SimulationStore`（进程内），方案汇总快照落 `plans` 表。
- **影响**：重启后 API-056/059/060/061 返回 40411；方案对比（API-049~053）不受影响。
  这是《数据库设计说明书》2.6 明确过的取舍，但使用者容易误判为缺陷。
- **建议**：若需要历史回溯，新增仿真记录表（`simulation_runs` + 明细子表或 JSON 列），
  并提供查询接口；若维持现状，则在前端「仿真历史」处明确提示「明细仅在本次运行内有效」。
- **验收标准**：重启后要么能查到历史明细，要么界面上有明确提示且方案对比仍可用。

### ISSUE-08 前端公共组件缺组件级单测

- **现状**：`package.json` 中**没有 Vitest**；`WarehouseLayout.vue`（408 行，含 Canvas 绘制与命中测试）
  与 `SeriesChart.vue` 仅由 27 项联调断言 + 人工验证覆盖。
- **依据**：《代码规范》7 节要求「前端用 Vitest 测试公共组件（平面图）与工具函数」。
- **建议**：引入 Vitest + @vue/test-utils，优先测三层：坐标换算（库位坐标 → 画布像素、
  y 轴翻转）、按层过滤、点击命中；Canvas 用 `getContext` 打桩或改用 OffscreenCanvas 断言调用序列。
- **验收标准**：`npm run test` 可执行，平面图组件的坐标换算与命中测试用例通过，并纳入提交前检查清单。

### ISSUE-09 端到端用例未覆盖 b/c 的接口

- **现状**：6 个 `*E2eTest` 全部针对 a 的模块（认证/RBAC/仓库/SKU/订单/导入导出）与安全链路；
  `/recommendations`、`/plans`、`/simulations/*`、`/orders/generate` 没有真实 HTTP 端到端用例，
  集成层仅由 `acceptance.ps1` 覆盖。
- **影响**：b/c 接口的权限注解、参数校验、错误码缺少回归保护；`acceptance.ps1` 需要手工启动服务。
- **建议**：按现有 e2e 模板（独立数据库 + 随机端口 + `run("--key=value")`）补 3 个用例类：
  推荐与配置、方案对比与导出、仿真与统计；每个类覆盖正常 + 403 + 参数非法三类。
- **验收标准**：`mvn test -Pe2e` 中 b/c 的接口有独立用例类且全绿。

### ISSUE-10 性能验证只在内存态

- **现状**：`PerformanceTest` 用 1 万个内存库位验证推荐计算 ≤ 5s（NFR-1），
  没有真实 MySQL 查询 + HTTP 序列化的耗时数据；仿真与出库统计也没有压测。
- **影响**：NFR-1 的结论「万库位秒级」缺少端到端证据；索引是否真正命中未经验证。
- **建议**：写一个压测脚本（数据生成 → 建 1 万库位 → 依次调用 API-041/055/058 并记录 P95 耗时），
  同时用 `EXPLAIN` 抽查三条主查询是否命中预期索引。
- **验收标准**：产出压测报告，API-041 在 1 万库位下 P95 ≤ 5s，且主查询命中
  `idx_locations_warehouse_status` 等预期索引。

### ISSUE-11 `plans.result` 同名字段两种口径

- **现状**：入库仿真先写「布局口径」（各分配库位到出库口距离的统计），
  出库仿真后用「订单口径」（实际拣选路程）**覆盖同名字段**，语义随写入时机变化。
- **影响**：同一列在不同方案上含义不同，对比时容易误读；报告导出也无法说明用的是哪种口径。
- **建议**：在 `result` JSON 内增加显式标识（如 `"metricScope": "layout" | "order"`），
  并在 API-049/051 的响应与前端列表上体现；`PlanResult` 已是 record，加字段兼容性可控。
- **验收标准**：方案列表能区分「仅入库仿真」与「已完成出库仿真」两种状态，报告里注明口径。

### ISSUE-12 随机订单集无结构化标记

- **现状**：API-062 生成的订单只把「随机订单集生成」写在 `orders.remark` 里，靠文本识别。
- **影响**：无法按批次统计、无法批量回滚；多次生成后会混在一起（当前演示库中已累积 80+ 张）。
- **建议**：给 `orders` 增加 `order_set_id`（或复用 `remark` 存结构化 id），
  API-062 返回该 id，并新增按批次查询/删除的能力。
- **验收标准**：能查询「某次生成的所有订单」并批量删除，且不影响手工录入的订单。

## 4. P3：优化项

### ISSUE-13 前端包体偏大

- **证据**：生产构建产物 `index-*.js` = 1 267 kB（gzip 410 kB）、`SeriesChart-*.js` = 1 037 kB（gzip 344 kB）。
  原因是 Element Plus 全量注册（含全部图标）与 `import * as echarts from 'echarts'` 全量引入。
- **建议**：Element Plus 改按需自动导入（`unplugin-vue-components`）；ECharts 改按需引入
  （只用柱状/折线 + 提示框 + 图例）；图标按名注册而非全量。
- **验收标准**：首屏 JS gzip 后 ≤ 200 kB，ECharts 分包 ≤ 150 kB，功能不减。

### ISSUE-14 后端端口在两处定义

- **现状**：`application.yml` 的 `server.port` 与 `frontend/vite.config.ts` 的代理目标各自写死；
  本轮就发生过「后端改成 8081、前端仍代理 8080」导致前端全部请求失败。
- **建议**：前端代理目标改从环境变量读（如 `VITE_PROXY_TARGET`，默认 8081），
  或统一由 `.env` 注入；在 README 里只保留一处说明。
- **验收标准**：改动后端端口时只需改一处（或改环境变量），前端无需改代码。

### ISSUE-15 Flyway 认领既有库后不再校验 V1~V3

- **现状**：`baseline-version` 默认为 3，被认领过的数据库不再对 V1~V3 做校验和比对，
  如果有人误改了已发布的迁移脚本，Flyway 不会报错。
- **建议**：在 CI 里加一步「空库全量执行 V1~Vn」的校验（临时库），保证迁移脚本本身始终可执行且与 `schema.sql` 一致。
- **验收标准**：CI 中存在该步骤，且 `python backend/tools/build_schema_sql.py` 产物与脚本一致。

### ISSUE-16 权限变更需重新登录生效

- **现状**：权限码写在 JWT 里，管理员改权限后，受影响用户需重新登录（默认 Token 有效期 8 小时）。
- **建议**：可选方案——① 缩短 Token 有效期并加刷新机制；② 在角色/权限表加版本号，
  每次请求比对版本，不一致则要求重新登录；③ 维持现状但在界面上给出明确提示。
- **验收标准**：改权限后，被影响用户的下一次请求要么立即生效，要么收到「权限已变更，请重新登录」的明确提示。

### ISSUE-17 CORS 白名单与接口文档的小缺口

- **现状**：`wms.cors.allowed-origins` 只配了 `localhost:5173` 与 `127.0.0.1:5173`；
  而 `npm run preview` 用的是 4173（靠 `/api` 代理同源规避，直连会跨域失败）。
  另外 `/api/v1/health` 端点存在但未写入《接口文档》。
- **建议**：把 4173 加入白名单（或改为按需配置）；把健康检查端点补进接口文档（标注为非契约的内部自检端点）。
- **验收标准**：从前端 4173 直连后端（`VITE_API_BASE_URL` 指向后端）可正常调用；接口文档包含该端点。

### ISSUE-18 分区由巷道派生的时效性

- **现状**：库位分区（品类）由所属货架的 `racks.aisle` 经映射派生，不落库。
- **影响**：若把某货架的巷道从 A 改成 B，既有货物的分区归属会**在展示与后续评分中改变**，
  但已保存的历史方案不变，可能造成「同一库位在两个方案里分区不同」的观感。
- **建议**：在货架更新接口上增加提示（改巷道会影响分区），或在方案快照 `params` 中已记录的
  `zoneAisleCategory` 基础上，在方案详情页展示当时的映射（当前 `params` 已写入该映射，前端未展示）。
- **验收标准**：修改巷道时有明确提示；方案详情可查看当时使用的分区映射。
