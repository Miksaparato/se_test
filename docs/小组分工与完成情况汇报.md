## 二、小组分工

### 2.1 分工原则

《任务分工文档》确定了 5 条原则，实际执行中也确实起到了作用：

| 原则 | 落地方式 |
| --- | --- |
| 端到端全栈切片 | 每人「后端模块 + 对应前端页面」成套交付，避免只写后端或只画界面 |
| 算法深浅搭配 | 核心算法（推荐评分、仿真引擎）与常规 CRUD、横切安全（RBAC）交叉分配 |
| 关键路径优先 | 推荐引擎与仿真引擎为关键路径，由专人负责；RBAC 以中间件横切，可并行 |
| 公共基础全员共建 | 数据库模型、REST 契约、鉴权中间件、平面图组件由牵头人产出、全员评审后冻结 |
| 依赖最小化 | 接口契约提前冻结，三人并行开发，只在联调阶段集中集成 |

### 2.2 三人分工总览

| 成员 | 角色定位 | 负责模块 | 后端包 | 前端页面 |
| --- | --- | --- | --- | --- |
| **谢卓成（a）** | 数据底座 + 安全 | 基础数据管理、用户与权限（RBAC）、登录认证 | `com.wms.data.*`、`com.wms.security`、`com.wms.domain` | 登录页、5 个数据管理页、用户/角色管理、路由与按钮权限 |
| **王轹文（b）** | 核心算法 + 分析 | 库位智能推荐、方案对比与优化建议、报告导出、参数校准 | `com.wms.recommend.*` | 入库推荐页、结果对比页、权重与规则配置页 |
| **曾远均（c）** | 仿真引擎 + 可视化 | 入库策略仿真、出库仿真与路程统计、随机订单集、平面图与图表 | `com.wms.simulation.*` | 仓库总览页、策略仿真页、公共平面图组件、统计图表 |

工作量与难度按《任务分工文档》第 10 节量化：综合负载 a = 62、b = 59、c = 62（相对均值偏差 +1.6% / −3.3% / +1.6%），
三人均覆盖前后端，最大差 3 点，属于均衡分配。

### 2.4 冻结契约与跨模块协作点

三人能并行的关键，是把耦合点收敛到 **5 处**，并且都用**数据结构**而非函数调用解耦：

| 协作点 | 提供方 | 消费方 | 解耦方式 |
| --- | :-: | :-: | --- |
| 数据库表结构 | a | b、c | 表/字段/索引冻结，实体与 Mapper 统一由 a 提供 |
| 鉴权中间件 | a（横切） | 全部接口 | 权限码 + `@PreAuthorize`，401/403 响应结构冻结 |
| 库位状态更新 | a（库位模型） | b（采用推荐） | 仓储层 `occupyLocation(id, skuId)`，条件更新保证一库位一货物 |
| 评分接口 | b（API-041） | c（`smart` 策略） | c 直接复用 b 的 `ScoringEngine`，评分逻辑只实现一次 |
| 分配方案数据 | c（仿真产出） | b（对比与报告） | `plans.location_map` / `result` 两个 JSON 结构冻结 |

> **口播稿（第一部分，约 2 分钟）**
>
> 我们组的分工按《任务分工文档》执行，核心思路是**端到端全栈切片**：
> 我负责「数据底座 + 安全」，包括仓库、货架、库位、货物、订单这些基础数据的管理，
> 以及登录认证和基于角色的权限控制，前后端一共 40 个接口；
> 王轹文负责「核心算法 + 分析」，也就是库位智能推荐的评分模型、方案对比和报告导出，13 个接口；
> 曾远均负责「仿真引擎 + 可视化」，包括六种入库策略的仿真、出库拣选与路程统计、随机订单集，
> 以及我们三方共用的仓库平面图组件，9 个接口。
>
> 为什么这样分？因为我们希望每个人的工作既有后端逻辑也有前端界面，避免有人只写接口、有人只画页面。
> 同时三条线的技术难点是错开的：我这边是横切的安全与数据一致性，
> 王轹文那边是评分模型的算法深度，曾远均那边是仿真与图形渲染。
>
> 三人并行的前提是**契约先冻结**。我们在第一周就把数据库表结构、62 个接口清单、
> 鉴权中间件的用法、平面图组件的 props、距离计算口径这五件事定死，写成六份文档。
> 这五处也是我们全部的耦合点，而且都用「数据结构」而不是「函数调用」来解耦——
> 比如曾远均的「智能推荐」策略直接复用王轹文的评分引擎，方案数据用冻结的 JSON 结构在两人之间传递。
> 所以三人在大部分时间里可以真正并行，只在最后联调阶段集中集成。

### 3.3 八条验收标准达成情况

| 验收标准 | 达成证据 | 结论 |
| :-: | --- | :-: |
| 1. 可录入仓库与货物，平面图正确展示库位布局 | 建仓 → 建货架（一次批量生成库位）→ 建货物 → 布局接口返回货架与库位（含编码/坐标/层/状态/容量）与出库口坐标；总览页按层展示平面图、点击可查库位详情 | ✅ |
| 2. 带评分与理由的推荐排序，支持权重调整 | 推荐结果按综合评分降序，每条给出四个分项得分与中文理由；修改权重后重算即时生效；权重之和不为 1 被拒 | ✅ |
| 3. ≥4 种入库策略仿真（含智能推荐） | 内置 **6 种**策略（随机/就近/分区/分级/智能推荐/FIFO），对同一批入库明细逐一仿真并各自产出方案 | ✅ |
| 4. 出库仿真 + 总/平均路程统计 | 生成订单集 → 按「优先级降序 + 下达时间升序」逐单拣选；校验「总路程 = 各单之和、平均 = 总÷单数、耗时 = 总÷速度」，并返回拣选路径坐标 | ✅ |
| 5. ≥2 方案对比 + 量化对比 + 建议文字 | 勾选方案后返回指标表格（总路程/平均/高频货平均距离/重货违规数）、对比图与自动生成的优化建议；支持导出 Markdown / CSV 报告 | ✅ |
| 6. 数据导入导出 + 核心算法单测 | 货物与订单支持 CSV/Excel 导入（跳过/覆盖策略）与 CSV/JSON 导出（带 BOM，Excel 不乱码）；后端 176 个测试方法覆盖评分、策略、距离、约束 | ✅ |
| 7. RBAC 角色隔离与越权拦截 | 四个内置角色登录后权限码逐一比对；viewer 执行仿真被 403、访问用户管理被 403、查看布局放行、匿名 401；前端菜单与按钮按权限显隐 | ✅ |
| 8. 提供使用说明文档 | 10 份文档齐备：需求分析、需求规格、任务分工、接口文档、代码规范、数据库设计说明、鉴权中间件规范、使用说明、两份算法说明 | ✅ |

### 3.5 计划之外的额外产出

在完成最低要求之外，我们还补了这些（都属于「让系统真正可用」的部分）：

1. **可配置的距离口径**：除默认曼哈顿距离外，支持欧氏与「三维折线」（平面 + 层差 × 层高），
   可由接口参数切换，便于做口径对比实验；
2. **参数校准接口**：管理员可以在不保存的情况下按新权重/规则预览重新评分结果，比较参数改动带来的排序变化；
3. **一键演示数据脚本**：通过公开接口写入 1 仓库 / 3 货架 / 36 库位 / 5 货物 / 12 订单，可重复执行，不触碰权限种子数据；

5. **离线演示模式**：无数据库时可用 `--wms.repository=memory` 启动（内置演示数据），便于评审快速体验；
6. **模板内联类型标注等前端规范的统一**，以及把「公共平面图组件」做成 a、b、c 三方共用（不复制三份）。

## 四、个人工作小结

### 4.1 谢卓成（成员 a）—— 数据底座 + 安全

#### 几个关键实现

1. **安全边界放在后端**：过滤器链负责「有没有登录」（401），方法级 `@PreAuthorize` 负责「有没有这个权限」（403），

2. **库位批量生成**：一次 `in` 查询判重 + 同一事务批量写入，避免逐条查询与写入；

3. **导入导出的工程细节**：CSV 带 UTF-8 BOM 与 CRLF 行尾，用 Excel 直接打开中文不乱码；

5. **可切换的数据访问实现**：默认走 MySQL，另保留一个内存实现用于无数据库环境的演示与算法调试，

> 王轹文用它高亮推荐库位，谢卓成用它做仓库总览。它用 Canvas 绘制，所以上万库位也不卡。
>
> 印象最深的坑是：六种策略一开始全部报「没有可用库位」，仓库里明明有空位。
> 后来发现是库位容量默认 100，而货物尺寸算出来是 6000——一个单位不一致的问题，
> 让整个仿真功能全都跑不起来。这件事让我记住：**跨模块的同一个业务规则，只能有一处实现**。
>
> 不足的地方：第一次交付时我没考虑「使用者怎么知道操作生效了」，结果卡片在首屏之外，
> 造成「点了没反应」的误解；这个已经补进文档。

## 五、团队协作的经验与不足

### 5.1 有效的做法

1. **契约先冻结、再并行**：数据库表结构、62 个接口、鉴权中间件、平面图组件、距离口径五件事在第一周定死，
   三人全程只在这五处耦合，没有出现接口对不上的返工。
2. **算法与框架解耦**：算法写成无状态服务，可以纯单元测试；推荐算法在没有数据库的阶段就完成了单测。
3. **仿真与真实数据分离**：试算不落库，使「多策略对比」「清空重置」既简单又安全。
4. **插件式扩展**：策略与评分分项都能零改动新增，答辩时可以现场演示「新增一种策略」。
5. **脚本化验收**：把八条验收标准固化成 47 条断言，任何人任何时间都能复跑，结果可复现。
6. **阶段确认**：每个阶段结束先对齐「做了什么、怎么验证、还剩什么」，再进入下一阶段，避免方向性返工。

### 5.2 需要改进的地方

| 问题 | 改进措施 |
| --- | --- |
| 合并后未立即构建验证，损坏被带进集成分支 | 把「编译 + 构建 + 全量测试」作为合并的前置条件 |
| 质量检查脚本配置错误，长期「假通过」 | 检查项必须验证其有效性；关键脚本纳入提交前必跑清单 |
| 同一业务规则（容量、层高）在多处实现，出现口径不一致 | 硬约束只保留一处共享实现，并配单元测试 |
| 同一配置在两处定义（后端端口 / 前端代理） | 配置只留一处真源，改动时同步检查依赖方 |
| 页面反馈不足：结果在首屏之外、控制台无提示 | 长表单页操作后自动滚动到结果区；关键操作保留可观测痕迹 |

> **口播稿（收尾，约 1 分钟）**
>
> 最后总结一下我们小组的协作。做得好的地方主要是三点：
> 一是**契约先行**，五处耦合点全部冻结，所以三个人能真正并行；
> 二是**算法与框架解耦**，算法可以独立测试，推荐算法在还没有数据库的时候就完成了单元测试；
> 三是**把验收标准变成了可执行的脚本**，47 条断言随时能复跑。
>
> 需要改进的地方也很明确：合并代码后我们没有第一时间跑完整构建，导致一次集成事故；
> 质量检查脚本配置错误、长期「假通过」；还有同一条业务规则在两处实现导致口径不一致。
> 这三条我们都已经写进改进清单——核心教训是：**流程里的每一步检查，都要确认它真的在检查**。
>
> 我的汇报就到这里，谢谢大家。
