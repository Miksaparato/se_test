## 1. 分工原则

为保证分工**合理、公平、可并行**，本次拆解遵循以下原则：

1. **端到端（全栈）切片**：每人负责「后端逻辑 + 对应前端页面」的完整闭环，避免出现只写后端或只画界面的单边工作，工作量与成长性对等。
2. **算法深浅搭配**：核心算法（推荐引擎、仿真引擎）与常规 CRUD、横切安全（RBAC）交叉分配，避免某人独揽全部高难度或全部低难度任务。
3. **关键路径优先**：推荐引擎与仿真引擎为关键路径，由专人负责并保证正确性；RBAC 以中间件形式横切，提前约定接口后可并行。
4. **公共基础全员共建**：数据库模型、REST API 契约、鉴权中间件、公共平面图组件等，由牵头人负责、全员评审确认，避免接口不一致风险。
5. **依赖最小化**：通过提前冻结接口契约，让三人可并行开发，仅在联调阶段集中集成。

## 6. 关键接口与协作契约

为避免三人并行时接口不一致（对应风险 10 节「三人并行开发接口不一致」），冻结以下契约：

| 契约 | 提供方 | 使用方 | 冻结要点 |
| --- | --- | --- | --- |
| 数据库表结构 | a | b、c | 表/字段/索引，第 1 周冻结 |
| 鉴权中间件 | a | b、c | `requirePermission()` 用法、403 返回格式 |
| 平面图组件 | c | a、b | `renderLayout()`、`highlight(locIds)`、`drawPath(points)` |
| 分配方案数据结构 | c | b | 方案对象字段（策略名、参数、库位占用映射、统计结果） |
| 推荐结果数据结构 | b | c（智能推荐策略复用） | 评分接口入参/出参 |

> 依赖关系：c 的「智能推荐策略」需调用 b 的评分接口；b 的「方案对比」需消费 c 产出的方案与统计结果。二者通过冻结数据结构解耦，可并行开发。

## 7. 工作量均衡说明

| 维度 | a | b | c |
| --- | --- | --- | --- |
| 后端模块 | 基础数据、RBAC（8 项） | 推荐引擎、方案对比、性能与调参（9 项） | 入库仿真、出库统计、订单生成（8 项） |
| 前端页面/组件 | 登录、数据管理、权限（4 项） | 推荐、对比、配置（4 项） | 平面图组件、总览、仿真、路径（5 项） |
| 算法难度 | 低（CRUD + 鉴权为主） | 高（评分模型为核心） | 中高（仿真 + 距离 + 约束） |
| 横切/共享责任 | 数据底座、鉴权 | API 契约牵头 | 公共可视化组件牵头 |
| 关键路径 | 数据/安全基础 | 核心推荐算法 | 仿真统计 |

**均衡结论：**

- a 面广但算法浅，承担数据底座与横切安全，是系统稳定运行的「地基」；
- b 面窄但算法深，承担评分模型这一核心关键路径；
- c 图形与仿真并重，承担共享可视化组件与随机订单集生成，工作量最多但单件复杂度可控。

三者分别覆盖「数据/安全」「算法/分析」「仿真/图形」，交叉覆盖前后端，无一人只做边角工作，总体均衡。
