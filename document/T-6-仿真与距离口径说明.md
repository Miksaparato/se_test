## 1. 距离口径（COM-6，冻结）

全部距离计算统一走 `com.wms.simulation.distance.DistanceUtil`，**禁止各处自行实现**
（《代码规范》4.5）。默认口径为曼哈顿距离。

| 口径 | 标识 | 公式 | 用途 |
| --- | --- | --- | --- |
| 曼哈顿距离（默认） | `manhattan` | `d = \|x₁-x₂\| + \|y₁-y₂\|` | 推荐「就近度」、入库「就近分配」、出库「搬运路程」 |
| 欧氏距离 | `euclidean` | `d = √((x₁-x₂)² + (y₁-y₂)²)` | 对比实验 |
| 三维折线距离 | `polyline` | `d = \|x₁-x₂\| + \|y₁-y₂\| + \|layer₁-layer₂\| × 层高` | 让高层库位的取货行程更接近实际 |

- 坐标 `(x, y)` 与层号 `layer` 取自 `locations` 表；出库口坐标取自 `warehouses.exit_x / exit_y`。
- 接口入参 `distanceMetric` / `layerHeight` 可覆盖默认口径（API-055 / API-058），
  缺省与无法识别的取值一律回落到曼哈顿口径，**不报错**。
- 单位：坐标与层高的单位由部署方统一（演示数据以「格」为单位）。

**搬运路程的定义**（《需求分析文档》1.4 术语表）：*从库位到出库口（或库位间）的移动距离*。

> 因此本系统统计的是**行程里程**：每访问一个库位计一次「库位 → 出库口」的单程距离，
> **不按件数重复计**。一张订单涉及多个库位时，按距出库口由近及远依次访问并累加各单程。
> 该口径与《接口文档》API-058 示例一致（3 张订单 → `totalDistance = 4755`、`avgDistance = 95.1`，
> 与 `hotAvgDistance = 76.4` 处于同一数量级，即为单程量级）。

## 2. 入库策略（C-B1 / C-B2）

### 2.1 插件式框架

```java
public interface InboundStrategy {          // simulation/strategy/InboundStrategy.java
    String name();                          // random / nearest / zoning / grading / smart / fifo
    String displayName();
    String description();
    StrategyPick pick(Sku sku, int quantity, List<Location> candidates, SimulationContext ctx);
}
```

- `StrategyRegistry` 在启动时注入全部实现并按 `name()` 建索引（`@Component` 自动注册）。
- **新增策略只需新增一个实现类**，仿真引擎、Controller、前端下拉框都无需改动（NFR-3）；
  策略清单由 API-054 动态返回。
- 策略必须无状态、构造注入依赖，便于纯 JUnit 单测（《代码规范》4.5 / 4.7）。

### 2.2 六种内置策略

| 标识 | 名称 | 选位规则 | 说明 |
| --- | --- | --- | --- |
| `random` | 随机分配 | 从候选空位中随机取一个 | 随机源种子固定，**同一种子结果可复现**；作为对照基线 |
| `nearest` | 就近分配 | `min d(库位, 出库口)` | 只看距离，不看货物属性 |
| `zoning` | 分区存储 | 先取分区品类 == 货物品类的库位，区内取最近；无命中则退化为就近 | 分区由 `racks.aisle` 经 `wms.zone.aisle-category` 派生 |
| `grading` | 分级存储 | `score = weightNorm × layerScore + turnoverNorm × proxScore` 取最大 | **不使用**可配置权重，规则固定、易解释 |
| `smart` | 智能推荐 | 复用 b 的 `ScoringEngine` 评分取最高分 | 跨模块协作点，**禁止复制评分逻辑**（《代码规范》4.5） |
| `fifo` | 先入先出 | `min 库位编码` | 规则固定、结果稳定 |

其中分级存储的分项（各归一化到 `[0,1]`）：

```
weightNorm   = clamp(weight / maxWeightNorm)
turnoverNorm = clamp(turnoverRate / maxTurnover)
layerScore   = (maxLayer - layer + 1) / maxLayer     // 层越低越大，重货受益
proxScore    = (dMax - d) / (dMax - dMin)            // 距出库口越近越大，高频货受益
```

### 2.3 一次仿真的执行流程（C-B3 / API-055）

```
校验仓库与策略
  → 取仓库当前空闲库位（free）
  → 构建 SimulationContext（出库口坐标、规则、权重、分区映射、距离口径、随机种子、占用快照）
  → 对 items 逐项：
        硬约束过滤候选（空闲 + 容量）
        → 策略选位 → 立即在上下文中标记该库位已占用
        → 记录 {库位, 理由, 适配分, 软约束告警}
  → 形成方案：location_map（库位 → {skuId, quantity}）+ 布局口径统计 + 参数快照
  → 落 plans 表（c 写、b 读）
```

**仿真不改库**：整个过程**不写 `locations` 表**（《数据库设计说明书》5.2「仿真需在不改库的前提下试算」）。
只有「采用推荐」（API-043）这类明确动作才会真正占用库位。「清空重置」（API-057）因此只需
丢弃内存记录并删除该次仿真产出的方案快照，基础数据不受影响。

## 3. 约束校验（C-B7，对应《需求分析文档》4.4）

三条约束按「硬约束 / 软约束」区别对待，这是本模块最重要的口径：

| 约束 | 类型 | 处理方式 |
| --- | --- | --- |
| 一个库位同一时刻最多一种货物 | **硬** | 候选只保留空闲库位；仿真过程中被选走的库位立即移出候选；落库时用条件更新 `WHERE status='free'` 兜底 |
| 货物尺寸不得超出库位容量 | **硬** | 体积 = 长×宽×高 > `locations.capacity` 直接排除（未录入尺寸则视为无该约束） |
| 重货禁止分配到超过预设层高 | **软** | **不排除候选**，而是判定 + 计数：`smart` / `grading` 会主动避开，`random` / `nearest` / `zoning` / `fifo` 可能命中，命中记为该方案的 `violations` |

> **为什么重货层高是软约束**：若所有策略都强制过滤，「重货层位违规数」这一对比指标将恒为 0，
> 失去 FR-5.1 的意义。《接口文档》API-051 示例中「随机分配」违规 5 处、「就近分配/智能推荐」为 0，
> 正是这个语义。阈值 `heavyWeightThreshold` / `maxLayerForHeavy` 由 b 的 API-046 配置，管理员可调。

容量判定由 `SkuSize.fitsWithin(capacity)` 统一提供，**b 的推荐引擎与 c 的约束校验共用同一实现**，
避免出现「推荐得出来的库位，仿真判为不可用」的口径分裂。

## 4. 出库仿真与路程统计（C-B4 / C-B6，API-058 ~ API-061）

### 4.1 拣选顺序（FR-4.1 / 算法 4.3）

订单按 **`priority DESC, placed_at ASC`** 排序（高优先级先出库，同级按下达时间先来先服务），
命中索引 `idx_orders_status_priority_placed`。前端「订单管理」页也用同一排序，语义一致。

### 4.2 库存来源两种模式

| 模式 | 触发条件 | 库存来源 | 用途 |
| --- | --- | --- | --- |
| 方案模式 | 请求带 `planId` | 该方案的 `location_map` | 「同一批货物、不同入库策略」的方案对比（FR-5.1） |
| 实际模式 | 只带 `warehouseId` | `locations` 中 `status='occupied'` 的库位 | 复盘当前真实库存的出库效率 |

### 4.3 逐单拣选

```
对每张订单：
    取其 SKU 的所有在库库位，按「距出库口由近及远」排序
    → 依次取货直到凑够订单数量（一库位一货物，故可能跨多个库位）
    → 单订单路程 = Σ(各取货库位到出库口的单程距离)
    → 拣选路径 = [库位₁, 出库口, 库位₂, 出库口, ...]
    库存不足或货物不在任何库位时：记录 warning，已拣部分照常计入路程
```

### 4.4 统计口径（FR-4.2）

| 指标 | 公式 |
| --- | --- |
| `orderDistances[i]` | 第 i 张订单的单程路程之和 |
| `totalDistance` | `Σ orderDistances`（总搬运路程） |
| `avgDistance` | `totalDistance ÷ orderCount`（平均每单路程） |
| `estimatedTime` | `totalDistance ÷ speed`（耗时估算，秒；速度缺省 1.0 格/秒） |
| `hotAvgDistance` | 高频货（周转频次 ≥ 0.5）各次取货的单程距离均值 |

> `hotAvgDistance` 是 FR-5.1 的对比指标之一：高频货离出库口越近，该值越小。

### 4.5 方案统计回填（c 写、b 读）

`plans.result` 的结构是冻结的（《数据库设计说明书》2.6）。写入时机分两段：

1. **入库仿真产出的方案**先写**布局口径**：`totalDistance / avgDistance / hotAvgDistance` =
   各分配库位到出库口距离的统计（每库位计一次），`violations` = 重货层高违规数，
   `orderCount = 0`、`estimatedTime = 0`。目的是让方案一产出就有可对比的量化指标。
2. **对该方案跑出库仿真（API-058）后**，用**订单口径**的真实统计覆盖上述四项，
   并补上 `orderCount` 与 `estimatedTime`。

两种口径的差别只在「路程覆盖的对象」：布局口径看「货放得离出库口多远」，
订单口径看「这批订单实际要走多少路」。`violations` 在两段都按同一规则计算，数值一致。

## 5. 随机测试订单集（C-B8，API-062）

- 输入：`count`、可选 `skuIds`、`priorityRange`、`quantityRange`、`timeRange`、`randomSeed`。
- 输出：落库为 `pending` 订单（可**直接**喂给 API-058），并回传 `orderIds` 与本次使用的
  `randomSeed`。
- **可复现性**：同一仓库 + 同一参数 + 同一种子 → 必然生成同一批订单，便于报告标注实验条件与回归测试。
- 落库走 a 的 `OrderService.createOrders(...)`，内部为**一条批量插入 SQL**
  （`mapper/OrderMapper.xml`），不在循环里逐条写库（《代码规范》4.4）。

## 6. 性能考量（NFR-1）

| 场景 | 设计 |
| --- | --- |
| 取空闲库位 | 一次 `WHERE warehouse_id = ? AND status = 'free'`，命中 `idx_locations_warehouse_status`，不在循环里查询 |
| 分区派生 | 货架一次批量取回建 Map，库位就地填充分区，避免逐库位查货架（N+1） |
| 出库拣选 | 先按 SKU 建一次「SKU → 在库库位（已按距离排序）」索引，再逐单消费 |
| 策略选位 | 单次选位 `O(候选数)`；`smart` 复用 b 的评分引擎（万库位级已由 b 的 `PerformanceTest` 覆盖 ≤5s） |
